# Coding standards

How code in this repo is written. ESLint, `tsconfig.json` and clippy enforce
formatting and the mechanical rules; this file holds only what they cannot: layout,
module shape, testing strategy and the conventions of generated scripts. Vocabulary
for the domain comes from `CONTEXT.md`; vocabulary for module shape (module,
interface, implementation, adapter, seam, depth) comes from the codebase-design
skill and is used in that exact sense here.

## Repository layout

Feature-based on the Vue side so a feature's view, state and tests sit together.
Module-based on the Rust side so each hardware or file concern has one home.

```
src/                      Vue renderer
  main.ts  App.vue
  ui/tokens.css           design tokens (the rule for them lives in DESIGN.md)
  ui/                     shared primitives (Button.vue, Field.vue, ...)
  domain/                 pure TypeScript types and validation; imports nothing from Tauri
  domain/generated/       shared types generated from Rust by ts-rs; never hand-edited
  tauri/commands.ts       the only file that calls invoke(); typed wrappers per command
  test/                   test helpers (withSetup, commands.ts mock factory)
  features/
    layouts/  monitors/  rdp/  audio/  shortcuts/  settings/
                          each: *.vue, use*.ts, *.store.ts (Pinia), *.test.ts
src-tauri/
  src/
    commands/             thin: deserialize args, call one function on app, map AppError
    app.rs                composition root: config store, script runner, the latest probe and the running
                          switch under one app root; orchestration that spans modules (capture is probe
                          plus store); app/switch.rs, app/log.rs, app/diagnostics.rs and app/transfer.rs split it by concern
    dialog.rs             the one place a native file dialog is shown; callers take the chosen path
    config/               typed Config, JSON under %LOCALAPPDATA%\layoutswap, schema version and migrations
                          (nothing roams: layouts hold device paths and GPU identities, so the whole
                          app root is machine-bound; Export config is the way to move between machines)
    script/render.rs      Layout + Config -> Script text
    script/run.rs         the only place powershell.exe is spawned
    hardware/             probe(): runs the probe script and parses JSON into Monitor and AudioEndpoint
    shortcuts/            writes the per-layout .lnk and registers the scheduled task, through generated scripts (ADR-0001)
  templates/*.ps1.tmpl    included by render.rs at compile time
  tests/golden/*.ps1      rendered output for fixture configs
docs/adr/  docs/agents/  docs/design/  docs/research/  docs/windows-behaviour.md
samples/                  reference output, hand-written, never executed by tests
```

A feature owns its tests. A test file sits beside the file it tests.

## Modules and seams

Commands are shallow; modules are deep. A Tauri command deserializes, calls one
module function, and maps the error. Everything worth testing lives behind it.

**Tauri command seam.** The interface is the set of named commands and their serde
types. `src/tauri/commands.ts` is the sole TypeScript implementation of calling
them. Feature tests mock `commands.ts`; nothing else in `src/` imports `invoke`.

**Script renderer** (`script::render`). Interface: `render(layout, config) -> Script`.
This is the deep module of the app: every PowerShell 5.1 quirk, escaping rule, step
ordering and logging convention lives here, so every feature gets them for free.
Tested with golden files under `src-tauri/tests/golden/`. The samples are
inspiration for the templates, never fixtures.

**Windows hardware adapter** (`hardware`). Interface: `probe() -> Inventory`. The
implementation runs a probe script through `script::run` and parses its JSON.
`script::run` sits behind a `ScriptRunner` trait so tests supply a fake runner that
returns canned JSON. Hardware knowledge lives in this one directory.

**Config store** (`config`). Interface: `load() -> Config` and `save(Config)`. The
implementation is one JSON file with a schema version and forward migrations. The
path is injected so tests use a temporary directory.

Shared types are defined once in Rust and generated for TypeScript with `ts-rs`.
The generated file is committed and regenerated by a script, never hand-edited.

## Vue

Composition API only, every component `<script setup lang="ts">` with typed
`defineProps` and `defineEmits`.

### Functions first, composables second, components last

Business logic is pure functions in `domain/`. Composables are a **thin** layer of
reactivity over those functions. Components stay **humble**. The order matters
because each layer is cheaper to test than the one above it: a pure function tests
with no Vue at all, a composable tests as a function call, and a component needs a
mounted DOM. Push every assertion to the lowest layer that can make it.

| Layer | Holds | Example |
|---|---|---|
| `domain/` | Pure functions and types. No Vue imports, no side effects. The functional core, and where most logic lives. | `validateLayoutName`, `orderSteps` |
| Composables | Thin reactivity over domain functions: refs, computed, watchers, calls through `commands.ts`. | `useLayoutDetail`, `useMonitorProbe` |
| Pinia stores | State that outlives one component or is read by more than one feature, plus actions that orchestrate across features. A store composes domain functions and composables rather than reimplementing them. | `layouts.store.ts` |
| Components | Template, props, emits, and local UI state such as open, hovered, or focused. Wires composables together. | `LayoutDetail.vue` |

**When to extract a composable.** Extract when the code holds a decision, an
effect, or a call across a seam: branching, async work, error handling, a
watcher, or a call through `commands.ts`. State that only the template cares
about, such as which tab is open or whether a row is hovered, stays in the
component. A composable that would only relocate a few lines with no decision in
them is not worth its file; put the logic in a domain function and call it from
the component instead.

**Composables carry no hidden state.** Every ref a composable creates is created
inside the function body, so two callers get two instances. State that must be
shared is a store's job.

### Composable conventions

Follow the official guide, plus the rules below.

- **One responsibility.** A composable has one reason to change. `useLayoutDetail`
  that also probes hardware becomes two composables that the component wires.
- **Name and file.** `useThing` in camelCase, in `useThing.ts` beside the feature
  that owns it. Composables shared by two features move to `domain/` only if they
  have no Vue imports; otherwise the features share a store.
- **Inputs.** Accept `MaybeRefOrGetter<T>` and normalise with `toValue()` so
  callers can pass a value, a ref or a getter. Four or more parameters become one
  options object.
- **Outputs.** Return a plain object of refs, computeds and functions so
  destructuring keeps reactivity. Expose failures as a returned `error` ref, never
  by logging inside the composable.
- **Order inside the function.** Inputs, state, computed, functions, watchers,
  lifecycle hooks, return. A reader finds the same shape in every file.
- **Side effects.** Register cleanup with `onScopeDispose` (or `onUnmounted` when
  DOM-bound) in the same composable that created the effect.
- **Call site.** Called synchronously at the top level of `<script setup>` or of
  another composable, so Vue can bind lifecycle and scope.

### Stores

One Pinia store per feature that shares state, defined with the setup syntax so it
reads like a composable with identity. Store actions are the place for
orchestration that touches more than one feature; the steps of that orchestration
are still domain functions and composables the action calls. A store is the seam
between features: a feature reads another feature's state through that feature's
store, never through its components or composables.

### Styling

Plain HTML elements and scoped CSS. Every colour, font, radius and spacing value
comes from `src/ui/tokens.css`; a component declares no literal values of its own.
Native elements first: `<dialog>` for modals, `<details>` for collapsed sections,
`<select>` and `<input>` styled through tokens. Reka UI is the one permitted
component dependency, used only where a native element cannot meet keyboard and
screen-reader needs: combobox, dropdown menu, and the reorderable steps list.
No utility framework and no component framework with its own base CSS.

### Testing Vue code

- A domain function is tested as a plain function. This is where most tests live.
- A composable is tested directly: call it, drive its inputs, assert its outputs.
  When it registers lifecycle hooks, run it inside a throwaway component with a
  small `withSetup` helper in `src/test/`. A composable thin enough to have no
  decision of its own needs no test beyond the domain function it wraps.
- A component is tested with Vue Test Utils for what it renders and what it emits.
  Logic assertions belong in the composable's test, so a component test that
  checks a computed value is testing the wrong layer.
- `commands.ts` is mocked in every renderer test. Nothing in a test reaches Tauri.

### Imports and files

- A feature imports from `domain/`, `ui/`, `tauri/commands.ts`, another feature's
  store, and itself.
- Types are explicit at seams and inferred inside functions. `unknown` at the
  edges, narrowed by validation in `domain/`.
- File names: `PascalCase.vue`, `useThing.ts`, `thing.store.ts`, `thing.test.ts`
  beside the source, `kebab-case.ts` for everything else.

## Rust

- One `AppError` per crate, built with `thiserror`, carrying a user-facing message
  and, where one exists, the log path. Every command returns `Result<T, AppError>`.
- `unwrap` and `expect` appear only in tests and in `main` startup where a failure
  should abort.
- Clippy runs with `-D warnings`.
- Module files are small; a module that grows past a screen splits by concern, not
  by type.

## Generated PowerShell

Generated scripts are the runtime. They follow one shape so a user can read any of
them and so golden tests stay stable. The probe is the one exception: it prints a
single JSON document on standard output and nothing else there, so it carries the
`#Requires` line and the header but no `USER SETTINGS` block, no log tee and no
progress lines; its failures go to standard error, and the app writes them to
`probe.log` in the app root.

- First line `#Requires -Version 5.1` (ADR-0004), then a comment header stating
  `generated by layoutswap`, the layout name and the render timestamp.
- A `USER SETTINGS` block comes next, holding every value the user chose, so the
  script reads as a record of the layout.
- Steps are idempotent: re-running a script that already applied is a no-op with a
  log line, never an error.
- Every line printed also lands in an append-only log with a timestamp, so a run
  from a shortcut can be checked afterwards.
- Each generated script is self-contained: interop code and layout data are
  embedded, so it runs alone from a shortcut. The app regenerates every script
  when the template changes; a script older than its template or its layout is
  stale.
- Step progress is one stable line format the app parses and a person can read.
  The exact format is defined once in the renderer and documented in its module
  header; every other line is log.
- Exit codes are documented in the header: 0 applied, 1 could not apply, 2 needed
  a user action (press the input button, run elevated).
- The 5.1 rules from `docs/windows-behaviour.md` are generator rules: copy, edit
  and write back nested structs; call typed non-generic wrappers; guard `Add-Type`
  with a `PSTypeName` check.

## Testing strategy

- Vitest with Vue Test Utils for `domain/` and each feature. Features test through
  their store or composable with `commands.ts` mocked.
- Rust unit tests for `config` (temp dir) and `script::render` (golden files). A
  golden test renders a fixture config and compares to the committed `.ps1`.
- Hardware tests are marked `#[ignore]` and run by hand on a real multi-monitor
  machine before a release, following the checklist in `CONTRIBUTING.md`.
- Replace, do not layer: when an interface test covers behaviour, the older unit
  test for the same behaviour is deleted.

## Naming

Identifiers, file names, commit messages and UI copy use the terms in `CONTEXT.md`.
A concept that has no term there is a signal to add one before naming code after it.

## Errors and logging

A user-facing error names the glossary term involved, says what to do next, and
includes the log path when a script ran. The log format is the generated script's
format above, so app logs and script logs read the same.

Two logs: `logs\layoutswap.log` for the app's own lines, and `switch.log` inside
each layout's folder, appended by that layout's script on every run, from the app
or from a shortcut. Every failure line carries the step it happened in and the
Windows error code when one exists.

Every failed switch offers **Save diagnostics**, which writes one zip containing
the app log, that layout's switch log, the last probe output, the generated script
and the config. The same action lives in Settings for failures that did not
surface as a switch result.
